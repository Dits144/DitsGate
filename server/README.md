# DitsGate local sandbox API

## ShopeePay official transaction status — fail-closed scaffold

This is **not** Shopee Partner portal scraping, a connection to static QRIS, or a payment-verification service. Backend-only onboarding settings are listed in `.env.example` (`SHOPEEPAY_ENV` = `uat` or `production`; client ID, secret, merchant/store external IDs). No credentials are bundled. `GET /api/v1/shopeepay/config` requires a merchant session and returns only `{data:{configured,environment,status:"not_verified",checkAvailable:false}}`; configured means settings are present, **not** a live connection. The UI must keep its submit button disabled while `checkAvailable` is false. `POST /api/v1/shopeepay/check` takes `{referenceId,amount}` (whole IDR) and requires a merchant session. It returns 503 without complete configuration or 409 for **every currently unbound reference**, including all `demo_only` transactions and QRISGate `provider_orders`; it never sends an upstream request from the HTTP route. Merchant test keys/admin sessions cannot use either route. No status, balance, ledger, or fee is changed.

`server/shopeepay.mjs` is an isolated dependency-injected test harness for the official Check Transaction Status payload: fixed Indonesian UAT/production hosts, POST `/v3/merchant-host/transaction/check`, `X-Airpay-ClientId`, `X-Airpay-Req-H` HMAC-SHA256/Base64 over exact raw JSON bytes, UUID `request_id`, `transaction_type:13`, amount ×100, 8-second timeout, and redirect rejection. Its signed-response fixture checks `request_id`, `errcode:0`, and `transaction.reference_id`, `merchant_ext_id`, `store_ext_id`, `amount`, `transaction_type`, `status`. It reports only `signed_response_received`, **never** `payment_verified`; it cannot be reached from HTTP and is not a live test. Signatures are verified on raw response bytes before JSON parsing. `X-Airpay-Resp-H` appears in an [older ShopeePay merchant integration PDF](https://wiki.monkeyenglish.net/assets/uploads/files/1662359292751-shopeepay_merchant_integration_pgw_4_52_vietnamese_docx_2_1.pdf), but the [current official Get Started page](https://product.shopeepay.com/integration/get-started) requires response-HMAC verification **without naming the response header**. Therefore its name has **not** been confirmed from the current official documentation: do not wire this harness to HTTP/live calls until ShopeePay onboarding confirms the header and a trusted, tenant-bound provider-created order is persisted. A signature by itself or a demo/static QRIS order is never proof of payment. The [official check API](https://product.shopeepay.com/integration/api/check-transaction-status) documents the fields; [transaction statuses](https://product.shopeepay.com/integration/common-objects) include successful status 3, distinct from `errcode:0` (a successful query, not necessarily a paid transaction).

### MPM dynamic QR fixture — belum koneksi live

[Dokumentasi resmi MPM](https://product.shopeepay.com/integration/api/merchant-presented-mode) menetapkan POST `/v3/merchant-host/qr/create` dengan `request_id`, `amount` (rupiah ×100), `currency:IDR`, `merchant_ext_id`, `store_ext_id`, dan `payment_reference_id`; respons sukses mencakup `qr_content`. `createShopeePayQrFixture` di `server/shopeepay.mjs` membangun permintaan ini dan memeriksa respons bertanda tangan dengan transport yang **wajib diinjeksi oleh tes**. Fungsi ini tidak punya route HTTP, tidak memakai global `fetch`, tidak mempersist order, dan tidak mengubah saldo. Fixture dengan `X-Airpay-Resp-H` hanya menguji bentuk parser berdasar materi lama; bukan verifikasi integrasi onboarding. `qr_url` sampel punya masa berlaku singkat dan sengaja tidak dipublikasikan. Konfirmasi header HMAC respons dan contoh respons UAT dari kanal onboarding, kemudian implementasikan penyimpanan order tenant-bound secara atomik sebelum mengaktifkan route live. QR statis dan transaksi `demo_only` tetap tidak memenuhi syarat.

Jalankan `node server/index.mjs` dari root proyek dengan Node.js 22.13+ (disarankan 24/26; membutuhkan `node:sqlite`). Pada host ini `npm.cmd run api` mengambil Node 20 dan **gagal**; gunakan `C:/Users/dits1/AppData/Local/hermes/tools/node-26.12.1-win32-x64/node.exe server/index.mjs` sampai PATH npm diperbaiki. Server hanya mendengarkan `127.0.0.1:5180`. Database lokal: `data/ditsgate.sqlite` (pastikan diabaikan Git). Atur `DITSGATE_DB` untuk path SQLite alternatif, `DITSGATE_API_PORT` untuk port alternatif.

**Bukan pembayaran nyata.** Endpoint webhook ada untuk validasi kontrak lokal, tetapi **tidak ada jalur pembuatan order QRISGate live**. Tidak memvalidasi mutasi bank, tidak pernah menandai transaksi sandbox `paid`. Transaksi hasil POST diberi status `demo_only` dan kode unik `0`; webhook hanya memproses tabel `provider_orders` terpisah yang harus diisi oleh integrasi server-side tepercaya (belum dibuat). Workspace React utama masih memakai localStorage. Halaman API & Webhook dapat login secara terpisah ke sandbox API lokal; sesi disimpan hanya di memori tab. Login UI yang lain, saldo demo, dan panel admin belum terhubung ke API ini. Jangan deploy sebagai layanan pembayaran.

Endpoint (JSON, bearer token kecuali health dan auth):
- `GET /api/health`
- `POST /api/auth/register` `{name,email,password}` (password minimal 12 karakter)
- `POST /api/auth/login` `{email,password}` → bearer token berlaku 24 jam; `POST /api/auth/logout`
- `GET, POST /api/v1/bank-accounts`; `PATCH, DELETE /api/v1/bank-accounts/:id`. Input `{bank,holder,number,isDefault?}`. Nomor rekening hanya keluar dalam bentuk masked. Tidak melakukan verifikasi kepemilikan rekening.
- `GET, POST /api/v1/qris`; `PATCH, DELETE /api/v1/qris/:id`. Input `{payload,provider?,name,city,mode,isDefault?}`. Payload EMVCo diperiksa CRC-nya, tetapi tidak membuktikan kepemilikan atau validitas merchant. Jangan gunakan payload sebagai dasar menerima pembayaran.
- `GET, POST /api/v1/transactions`; POST `{order_id,amount,qris_id?}`. Hanya menyimpan order sandbox. `qris_id` harus milik akun, atau dipilih dari QRIS default. Tidak menghasilkan QR dinamis dan tidak ada pembayaran.

Webhook sandbox: `POST /api/webhooks/qrisgate` menerima body JSON mentah dengan header `X-QRISGate-Event`, `X-QRISGate-Timestamp`, `X-QRISGate-Signature`, `X-QRISGate-Delivery-Id`. Set `QRISGATE_WEBHOOK_SECRET` **hanya di environment server**, jangan di frontend atau repo. HMAC-SHA256 dihitung atas byte `timestamp + '.' + rawBody`; window 5 menit, perbandingan constant-time, lalu cocokkan `external_order_id`, `transaction_id`, `base_amount`, `unique_code`, dan `total_amount` ke order provider yang telah dipersist. Delivery ID dedupe dan status order diubah atomik; status final tidak dapat ditimpa event baru. Tanpa secret endpoint merespons 503. **Jangan arahkan webhook akun QRISGate ke localhost ini**: callback publik yang sudah ada mungkin melayani aplikasi lain dan menggantinya akan mengganggu pembayaran mereka. Pastikan pengaturan per-key dan routing sebelum integrasi live.

Kontrak header dan payload flat diamati di https://qrisgate.web.id/docs; sampel pengaturan dari pengguna bukan bukti bahwa order live sudah tersambung. Cuplikan Express pada dokumentasi menggabungkan `timestamp + '.' + req.body` (Buffer) dengan operator `+`; implementasi di sini memakai `update(timestamp).update('.').update(bytes)` agar byte raw tidak dikonversi secara tak sengaja.

## Admin lokal, saldo dan topup

Set `DITSGATE_ADMIN_EMAIL` hanya pada environment server. **Email saja tidak memberi hak admin.** Registrasi publik untuk email cadangan ditolak, dan semua registrasi lain selalu `merchant` (field `role` dari klien diabaikan). Untuk mengaktifkan admin pertama kali, operator tepercaya harus membuat user baru **secara offline**, sebelum ada akun lain memakai email tersebut, dengan `bootstrapAdmin(db,{email,password})` dari `server/app.mjs`. Fungsi ini tidak mempunyai route HTTP, butuh email identik dengan environment dan password minimal 16 karakter, serta gagal jika email sudah terdaftar. Contoh jalankan lewat skrip operator lokal yang mengambil password dari kanal rahasia (jangan masukkan password sebagai argumen shell, frontend, atau file di repo). Bila ada akun lama yang sudah memakai email admin, hentikan bootstrap dan selidiki kepemilikannya; jangan elevasi akun itu. Route admin mensyaratkan role DB `admin` **dan** email yang cocok dengan environment pada setiap request; tanpa konfigurasi semua route admin 403. Penyelenggara harus mengelola reset/rotasi credential dan proteksi host SQLite secara terpisah.

Endpoint baru (JSON; bearer token untuk semuanya):
- `GET /api/v1/balance` → `{balance,currency:"IDR"}` dan `GET /api/v1/ledger` → `{data:[{id,amount,kind,sourceId,actorId,createdAt}]}` untuk pemilik akun; maksimum 100 entri terbaru.
- `GET /api/admin/merchants` → `{data:[{id,email,name,createdAt,balance}]}` (100 terbaru). `GET /api/admin/merchants/:id` → `{data:{id,email,name,createdAt,balance,ledger,topups}}`; ledger/topups maksimum 100 terbaru masing-masing. Password hash, token dan rekening tidak dikeluarkan.
- `POST /api/admin/topups` `{merchantId,amount}` (integer 1–999999999) → 201 `{data:{id,merchantId,amount,status:"pending",createdBy,createdAt,confirmedBy,confirmedAt,proofReference,note},instructions:{qrisPayload,notice}}`. Butuh `DITSGATE_ADMIN_TOPUP_QRIS` berisi payload nyata yang dikonfigurasi operator di sisi server. Jika belum ada, 503; **tidak ada kredit saat pembuatan intent**. Payload QRIS hanya dikirim ke bearer admin, bukan endpoint publik.
- `POST /api/admin/topups/:id/confirm` `{proofReference,note}` → `{data,balance,verification:"admin_confirmed_only"}`. Referensi bukti eksternal harus unik (6–128 karakter terbatas), catatan minimal 8 karakter; konfirmasi ulang/duplikasi referensi → 409. Transaksi SQLite mencatat admin aktor, waktu, bukti, dan kredit ledger sekali. Operator harus mencocokkan bukti dengan sumber bank/provider di luar aplikasi sebelum konfirmasi; aplikasi **tidak** memverifikasi pembayaran QRIS ataupun memastikan transfer benar-benar masuk. Jangan menandai ini `QRIS verified`.

Webhook `payment.paid` yang HMAC dan order persisted-nya lolos verifikasi mendebet **Rp100 sekali** (`paid_order_fee`) di transaksi yang sama dengan perubahan status/delivery. Jika saldo funded kurang dari Rp100, webhook mengembalikan 409, order tetap `pending`, delivery tidak tercatat; butuh penanganan retry/reconciliation secara manual atau oleh provider. Status final lainnya tidak dikenakan fee. Unique `(kind,source_id)` pada ledger dan delivery dedupe mencegah debit/kredit ulang melalui API. Ledger adalah jejak audit aplikasi; administrator yang memiliki akses tulis langsung ke SQLite masih bisa mengubah data, sehingga produksi memerlukan hak DB, backup, audit eksternal, rekonsiliasi, dan validasi operasional tersendiri. Tidak ada scraping portal Shopee atau klaim integrasi live.

## Kunci API merchant & konfigurasi webhook keluar (hanya lokal)

Hanya **sesi bearer merchant** yang boleh mengelola kunci dan pengaturan webhook; bearer admin ditolak. Kunci `dg_test_…` adalah kredensial local test, bukan `qg_live` atau token perangkat. Simpan respons pembuatan dengan aman: string kunci mentah hanya dikembalikan satu kali dan di database hanya ada SHA-256, prefix tersamarkan, waktu pemakaian terakhir, dan waktu revokasi. Jika hilang, buat kunci baru lalu cabut yang lama. Semua respons memakai `Cache-Control: no-store`; jangan catat respons berisi kredensial di log. Proteksi file SQLite dan transport API; server default hanya loopback, bukan layanan produksi.

- `POST /api/v1/api-keys` dengan `{name, webhookUrl?, qrisId?}` → 201 `{data:{id,name,prefix,webhookUrl,qrisId,createdAt,lastUsedAt,revokedAt,environment:"local-test",deliveryEnabled:false},key,notice}`. `qrisId` opsional harus milik merchant; `webhookUrl` adalah tujuan per-key, bukan endpoint masuk provider. Kunci bersifat unik dan acak; tidak ada field scope yang bisa dinaikkan oleh klien.
- `GET /api/v1/api-keys` → `{data:[...]}` hingga 100, tanpa raw key/hash. `PATCH /api/v1/api-keys/:id` menerima hanya field yang ingin diubah dari `{name?,webhookUrl?,qrisId?}` (minimal satu field); `name` wajib string non-kosong hingga 100 karakter jika diberikan. `webhookUrl:null` menghapus tujuan per-key agar konfigurasi akun menjadi fallback kelak, dan `qrisId:null` kembali memakai QRIS default akun. Tujuan URL harus lolos aturan HTTPS publik di bawah; QRIS harus milik merchant. Hanya sesi pemilik merchant yang boleh mengubah; field asing/isi tidak valid → 400, kunci merchant lain → 404, kunci dicabut → 409. Respons `{data}` berisi metadata terbaru, tanpa raw key/hash. `DELETE /api/v1/api-keys/:id` → `{ok:true}`; hanya pemilik, revokasi langsung menolak penggunaan berikutnya; milik merchant lain → 404. Buat kunci pengganti sebelum revokasi untuk rotasi. Kunci yang dicabut tetap tampil sebagai metadata audit.
- Kunci dipakai sebagai `Authorization: Bearer dg_test_…` **hanya** untuk `GET/POST /api/v1/transactions`; semua endpoint lain memerlukan sesi. Session bearer sebelumnya tetap berlaku. Pada kunci dengan `qrisId`, GET hanya menampilkan transaksi aset itu dan POST menggunakan aset itu secara default; aset lain ditolak. Status order tetap `demo_only`, tidak membuat tagihan atau callback.
- `GET /api/v1/webhook-settings` → `{data:{url,secretConfigured,createdAt,updatedAt,deliveryEnabled:false}}` tanpa secret. `PATCH /api/v1/webhook-settings` `{url:"https://merchant.example.com/callback"}` mengatur tujuan akun; `{url:null}` menghapus URL. `POST /api/v1/webhook-settings/rotate-secret` `{}` → `{data,secret,notice}`: random 32 byte, hanya ditampilkan di respons rotasi. Hash secret disimpan; rotasi sebelumnya langsung diganti. Secret ini **bukan** `QRISGATE_WEBHOOK_SECRET` untuk webhook masuk. Tidak ada endpoint untuk menampilkan kembali secret.
- URL harus HTTPS berhostname domain publik, tanpa IP literal, kredensial, fragmen, atau port non-443. Hostname khusus seperti `localhost`, `.local`, `.internal`, `.test`, `.invalid`, `.example`, dan `.onion` ditolak. Ini validasi konfigurasi sintaksis, **bukan** jaminan DNS publik: tidak ada DNS resolving atau permintaan HTTP. Tidak ada ping endpoint (404), tidak ada pengiriman webhook, dan `deliveryEnabled:false` hingga integrasi provider tepercaya dan mekanisme egress tahan DNS-rebinding/SSRF, redirect, timeout, serta retry selesai. Hash secret tidak dapat digunakan untuk menandatangani pengiriman kelak; desain secret harus diperluas dengan penyimpanan terenkripsi/secret manager sebelum delivery diaktifkan. Jangan mengklaim webhook terkirim dari URL yang tersimpan.

Contoh uji otomatis dengan Node 26: `C:/Users/dits1/AppData/Local/hermes/tools/node-26.12.1-win32-x64/node.exe --test tests/*.test.mjs`. Server membatasi origin browser ke `http://127.0.0.1:5179`; API ini masih **development-only**: tidak punya rate limit login, reset password, verifikasi email, atau pengelolaan secret produksi.
